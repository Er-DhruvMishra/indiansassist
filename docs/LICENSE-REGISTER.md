# Licence register

Our code: **AGPL-3.0-only** (`LICENSE`, `NOTICE`; decided 7 Nov 2026, superseding the "source available" decision of PRD section 15.5). Third party components we build on or run beside keep their own licences. Working agreement (contracts section 15): every new runtime dependency or Compose image is added here with its licence in the same change, and the register is reviewed at the end of every phase. The compatibility audit for distributing under AGPL-3.0-only is at the end of this file.

## Licence compatibility audit for AGPL-3.0-only (7 Nov 2026)

Question: can every component the project **ships** be distributed together with our AGPL-3.0-only code, and is every such component under an OSI-approved licence (SignPath Foundation's condition)? Sources: `pnpm licenses list --prod` for the npm production tree, `cargo metadata --format-version 1 --manifest-path agent/Cargo.toml` for every resolved Rust crate (all targets), `cargo tree -i <crate> --target all --all-features` for who pulls a crate in, and the rows above for Go, Gradle and SwiftPM. This is an engineering review, not legal advice.

**Scope and exemptions.**
- *Shipped* means the web app bundle, the api and recorder server images, the Windows, Linux and macOS agents and their installers, the Android and iOS apps and the browser extension.
- *Exempt* (not distributed with our code, so not part of the combined work): build-only and test-only tools (Xcode and Apple's developer tools, WiX, rpm, ansible-core, ansible-lint, cargo-deb, cargo-generate-rpm, cargo-zigbuild, Zig, XcodeGen, the Android Gradle Plugin and Gradle, the Go toolchain, Playwright and Chromium, JUnit, ESLint plugins, the Ubuntu Base test root file system, the sway and portal test stack); **system libraries** (Windows DLLs, Apple frameworks, glibc, libpipewire, libwayland, X11 libraries), which AGPLv3 section 1 excludes from the Corresponding Source; and separate services that run beside the api as their own unmodified processes, talked to over a network protocol (PostgreSQL, Valkey, coturn, nginx, SeaweedFS, Garage, OpenBao, Keycloak, any model server). Those are rows above with a "build only", "dev", "test" or "self-hosted service" status.

**Results.**
- npm production tree (all workspaces): MIT 165, Apache-2.0 32, ISC 14, BSD-3-Clause 5, BSD-2-Clause 1, Unlicense 1, MIT-0 1, BlueOak-1.0.0 1 (`sax`), 0BSD 1. All OSI-approved, all permissive, all compatible with AGPLv3 (Apache-2.0 is compatible with GPLv3-family licences in this direction).
- Rust (616 resolved registry crates, every target): MIT and/or Apache-2.0 for almost all; also ISC, BSD-2/3-Clause, Zlib, 0BSD, BSL-1.0, Unlicense, Unicode-3.0, MPL-2.0 (`option-ext`, through `tray-icon` -> `dirs`; unmodified, its source is public on crates.io, and MPL-2.0 is compatible with AGPLv3), and choices that include MIT where a crate offers LGPL or BSD-1-Clause alternatives (`r-efi`, `fiat-crypto`). All OSI-approved and AGPLv3-compatible, except F1 and F2 below. `hexf-parse` (CC0-1.0) is in the lock file but not in any build graph of the workspace (`cargo tree -i hexf-parse` prints nothing), so it is not shipped.
- `ring` 0.17.14: `cargo metadata` gives **Apache-2.0 AND ISC**, not "ISC AND MIT AND OpenSSL" as the rows used to say (newer ring releases dropped the OpenSSL-licensed code). Rows corrected. Both OSI-approved and compatible.

- Android (Gradle) and iOS (SwiftPM): Apache-2.0 and BSD-3-Clause, compatible (F3 resolved for both on 8 Nov 2026), subject to F4.

**Findings for a human decision** (as found; each resolution, decided by the owner and the coordinator and made on 7 Nov 2026, follows its finding; summary: F1 resolved, F2 resolved, F3 resolved for iOS (7 Nov 2026) and for Android (8 Nov 2026), F4 handled):
- **F1. `webpki-roots` 0.26.11 and 1.0.11: CDLA-Permissive-2.0, not OSI-approved.** It is Mozilla's list of root certificates as data, under a permissive data licence that asks only for the licence text to be kept; nothing in it conflicts with AGPLv3. It ships in the Windows, Linux and macOS agents through `tokio-tungstenite` (`rustls-tls-webpki-roots`) and `ureq`. Options: tell SignPath it is certificate data under a permissive data licence; or have the agent use the operating system's trust store (`rustls-native-certs` or `rustls-platform-verifier`, MIT/Apache-2.0), which removes the crate.
  - **Resolved (7 Nov 2026): the operating system's trust store.** `rustls-platform-verifier` =0.7.1 (MIT OR Apache-2.0) builds the one rustls config every `https://` and `wss://` call uses (`ia_platform::tls`, feature `tls`): Windows CryptoAPI chain building (which also fetches a root Windows has not cached and honours an organisation's own inspection root), the macOS Security framework, the Linux system store. tokio-tungstenite uses its rootless `__rustls-tls` backend and every connect passes that config as `Connector::Rustls`; ureq's `tls` feature (which always bundles webpki-roots) is off and `ia_waker::https` plugs the config in through ureq's `TlsConnector`. Plain `ws://` / `http://` to localhost is unchanged. `webpki-roots` is no longer in `Cargo.lock`; `cargo tree -e normal --target <triple>` for `ia-agent` (Windows default, Linux `media,x11,gui,linux-os`, Linux `portal`, macOS `media,macos,gui`), `ia-service` (`service`, `linux-service`, `macos-service`), `ia-desktop` (Windows default, Linux `linux`) and `ia-watchdog` shows no `webpki-roots`, `webpki-root-certs` or `epaint_default_fonts`. `webpki-root-certs` (CDLA-Permissive-2.0) is in the lock file only as the platform verifier's wasm32 dependency, which no shipped target builds. Tests: the config builds from the platform verifier (on Linux this fails on an empty system store), plain http to localhost still works, https goes through the OS-verified connector; network tests (`--ignored`) passed on Windows and Linux: crates.io and github.com verify, `self-signed.badssl.com` and `expired.badssl.com` are refused.
- **F2. `epaint_default_fonts`: (MIT OR Apache-2.0) AND OFL-1.1 AND LicenseRef-UFL-1.0.** egui embeds its default fonts in the agent binary. OFL-1.1 is OSI-approved; the Ubuntu Font Licence 1.0 (Ubuntu-Light) is not. Both allow bundling fonts with any software. Options: accept it as font data; or turn off egui's `default_fonts` feature and embed one OFL-1.1 or Apache-2.0 font in `ia-ui`.
  - **Resolved (7 Nov 2026): OFL fonts only.** `egui` with `default-features = false` and `eframe` without `default_fonts`, so `epaint_default_fonts` is no longer in `Cargo.lock`. `ia-ui` embeds Noto Sans Regular 2.015 and Noto Emoji 3.002 (both OFL-1.1, the upstream files byte for byte, sha256 in their rows above, `OFL.txt` beside them) and installs them with `FontDefinitions` in every eframe creator (`ia-ui/src/fonts.rs`). The consent window's check mark moved from U+2713 (in neither font) to U+2714 (Noto Emoji). Tests: the definitions hold exactly the two fonts for both families, the files are the pinned ones, and every fixed UI string, egui's own ellipsis and bullet, Latin/Greek/Cyrillic names and chat emoji have glyphs. Size: the removed set was 1.41 MB, the new one 2.41 MB.
- **F3. Android: BoringSSL inside the prebuilt libwebrtc of `stream-webrtc-android` 1.3.10.** The row lists BoringSSL as "OpenSSL/ISC". The original OpenSSL licence is not OSI-approved and the FSF regards it as incompatible with the GPL family. BoringSSL moved its code to Apache-2.0 in 2024. To do: read the BoringSSL revision and LICENSE inside the 1.3.10 AAR. If it still carries OpenSSL-licensed code, either move to a libwebrtc build with the Apache-2.0 BoringSSL, or (as the sole copyright holder) add an AGPLv3 section 7 additional permission for linking it. The same check applies to `stasel/WebRTC` 155.0.0 on iOS, whose M155 BoringSSL is expected to be Apache-2.0.
  - **Checked (7 Nov 2026). iOS: compatible, resolved. Android: not compatible, open (no library was swapped).**
    - *When BoringSSL changed licence:* commit `33d1049b1f730d2725bb09b2256fd5fe4c46b17e`, 3 Feb 2025, "Switch the license to Apache 2.0, matching OpenSSL upstream" (boringssl-review change 75852; GitHub mirror google/boringssl). Before it, `LICENSE` read "large parts of it fall under OpenSSL licensing" with "both the conditions of the OpenSSL License and the original SSLeay license" (new files ISC); after it, `LICENSE` is Apache-2.0, plus the Go licence for test-suite code that is not compiled into libcrypto or libssl. The first WebRTC milestone whose BoringSSL pin is after that commit is **M135** (branch-heads/7049, BoringSSL `748a2d281d33`, 39 commits after it); M134 (branch-heads/6998, `d4b6eb542d4f`) is 29 commits before it.
    - *Android, `stream-webrtc-android` 1.3.10:* the AAR in the local Gradle cache carries no LICENSE or NOTICE file; its `libjingle_peerconnection_so.so` (arm64-v8a) says "WebRTC source stamp 2024-04-15T04:12:23" and contains `third_party/boringssl/src/...` paths; the release notes of 1.2.3 to 1.3.3 say "Patch to m125" / "m125.3". WebRTC's `DEPS` at branch-heads/6422 (M125) pins BoringSSL `f94f3ed3965ea033001fb9ae006084eee408b861` (4 Apr 2024), 551 commits before the relicensing, whose `LICENSE` is the OpenSSL + SSLeay dual licence. That code is not OSI-approved and the FSF lists both licences as GPL-incompatible (the advertising clause), so the Android app as built cannot be distributed under AGPL-3.0-only without an exception, and fails SignPath's "OSI-approved licences for all components" for that app. No newer `stream-webrtc-android` exists (1.3.10, Sep 2025, is the latest).
    - *iOS, `stasel/WebRTC` 155.0.0:* the release names WebRTC branch-heads/8059, commit `5bd86a2f17a35dfc986b87d058f511e45805bd1d`; its `DEPS` pins BoringSSL `ebd832c3924065de594ffda62b376aeb2e4f61a9` (11 Sep 2026), 1,723 commits after the relicensing, whose `LICENSE` is Apache-2.0. Apache-2.0 is OSI-approved and compatible with GPLv3-family licences in this direction. (The xcframework is not on this Windows machine; the facts come from the upstream release page and WebRTC's `DEPS`.)
    - *Options for Android (owner's decision):* (a) move to a prebuilt libwebrtc at M135 or later, for example `io.github.webrtc-sdk:android` (BSD-3-Clause; 144.x and 150.x are on Maven Central), keeping the `org.webrtc` API the app uses, after checking its `DEPS` the same way; (b) build libwebrtc from source at M135 or later (BoringSSL is then Apache-2.0); (c) as sole copyright holder, add an AGPLv3 section 7 additional permission for linking the OpenSSL-licensed BoringSSL (this still leaves a non-OSI component for SignPath); or (d) keep the Android app out of signed releases until (a) or (b) lands.
  - **Resolved for Android (8 Nov 2026): option (a), `io.github.webrtc-sdk:android` 150.7871.04 (WebRTC M150).**
    - *Why this build:* `stream-webrtc-android` has nothing newer than 1.3.10 (M125; Maven Central metadata last updated 11 Sep 2025, and GitHub's latest release is the same 1.3.10). Of the maintained prebuilts on Maven Central, `io.github.webrtc-sdk:android` (the LiveKit-maintained webrtc-sdk project, BSD-3-Clause POM, releases every few weeks: 144.7559.15 on 5 Sep 2026, 150.7871.04 on 23 Oct 2026) and `org.jitsi:webrtc` 155.0.1 (M155, 22 Oct 2026) both qualify; both AARs carry the same `org.webrtc` Java API and native library layout. webrtc-sdk was chosen: like Stream's, it is a patched libwebrtc for app SDKs published as a single self-contained AAR (classes in `classes.jar`, no transitive dependencies), the same project publishes the package-prefixed variant LiveKit's Android SDK uses, its release notes name the exact source commit, and its POM names libwebrtc's real licence (Jitsi's POM says "Apache-2.0, MIT", the licence of its build scripts, not of libwebrtc). The newest release, 150.7871.04, is pinned; it ships arm64-v8a, armeabi-v7a, x86_64 and x86 (the app's `abiFilters` keep the first three).
    - *Evidence, the AAR itself* (`~/.gradle/caches/modules-2/files-2.1/io.github.webrtc-sdk/android/150.7871.04/.../android-150.7871.04.aar`, sha256 `1872dda4…c69c84c`, identical to Maven Central's): entries `AndroidManifest.xml` (WebRTC's BSD-style header, `package="org.webrtc"`), `classes.jar`, and `jni/<abi>/libjingle_peerconnection_so.so`; **no LICENSE or NOTICE file** is in the AAR (as with Stream's), so the licence facts come from the POM, the binary and the source it was built from.
