### 1.2 Architecture decisions (binding)

**(a) The agent is a WebRTC peer built on webrtc-rs (`webrtc` crate, MIT/Apache-2.0).** Phase A made the Desk an `RTCPeerConnection` that offers to the Assist and, since A.2, answers a second offer from the recorder; Phase B kept that shape. A native peer that speaks the same SDP, ICE, DTLS-SRTP, SCTP data channels and RTCP feedback plugs into the existing console (`RemoteView`, `getStats`, perfect negotiation), the existing `/signal` relay, coturn credentials (`desk:<sessionId>` principal), the pion recorder (A.2 N1-N5) and the audit chain without changing any of them. webrtc-rs is the Rust port of pion, which the recorder already uses, so interoperability problems surface in one place. The rejected alternative (PRD 3 P3 "QUIC or TLS over our relay") would have needed a second relay protocol, a second recorder input path and a console media decoder outside the browser; it is recorded as W6. Media stays DTLS-SRTP end to end: the TURN server forwards encrypted RTP/RTCP and SCTP and never holds a key.

**(b) An application-layer envelope encrypts the control, file and playbook data channels with per-session keys derived from a handshake over the data channel.** DTLS-SRTP protects against the network, not against a signaling server that rewrites SDP fingerprints and sits in the middle of two DTLS sessions. The envelope of §1.3 adds an X25519 key agreement (RustCrypto `x25519-dalek`, BSD-3-Clause; console `@noble/curves`, MIT; Android Tink, Apache-2.0), HKDF-SHA256 key derivation, XChaCha20-Poly1305 framing (`chacha20poly1305`, MIT/Apache-2.0; `@noble/ciphers`; Tink) and a key confirmation bound to the session id and both DTLS fingerprints. `sodiumoxide` is unmaintained; `libsodium-sys-stable` would add a C build to every target; the RustCrypto crates are pure Rust, audited, and the same primitives libsodium exposes (PRD 7 "libsodium / NaCl" is met by primitive, not by library; W7). Honest limit: an adversary who actively terminates DTLS on both sides **and** rewrites the handshake frames inside the data channel is detected only by the 6-digit security code (§1.3 step 7) that both UIs display and the two humans compare over voice. As in ZRTP, the code is safe at 20 bits only because each side **commits** to its key share (`sec.commit`, a hash of the share) before either share is revealed: a man in the middle must fix its own share towards one side before it has seen that side's share, so it gets one guess per leg and matches the two codes with probability 1e-6 per handshake, not with certainty. Every key generation (§3.7 rebuild, hand-over) is a fresh roll of that die, which is why the console re-confirms the code after every rebuild (step 7). A signaling server that merely reads, logs or replays sees nothing.

**(c) The Android host uses Google's libwebrtc for Android (BSD-3-Clause, prebuilt `io.getstream:stream-webrtc-android`, Apache-2.0 wrapper) with the same protocol.** `ScreenCapturerAndroid` wraps `MediaProjection` into a video track, `HardwareVideoEncoderFactory` gives VP8/H.264 hardware encoding, and the SDP/ICE/DTLS stack is the one Chrome ships, so the console, TURN and recorder see a familiar peer. The Kotlin code implements only what the agent implements: `/signal` client, consent, indicator, the §1.3 handshake (Tink), `ia.control` with the Android op subset (§12.4), files, chat, voice.

### 1.3 Secure channel handshake (`ia.sec`) and frame format

Data channels of a P3 session (created by the Desk **exactly once per peer connection**, before the first offer, `ordered: true`, reliable, `binaryType = 'arraybuffer'`): `ia.sec`, `ia.chat`, `ia.annot`, `ia.file`, `ia.ctrl`, `ia.control`, `ia.playbook` (`P3_DATA_CHANNEL_LABELS`). **Encrypted channels** (`SEC_ENCRYPTED_LABELS`): every label except `ia.sec`, i.e. `ia.control`, `ia.file`, `ia.playbook`, `ia.chat`, `ia.annot`, `ia.ctrl`; the A/B JSON messages of `ia.chat`, `ia.annot`, `ia.ctrl` travel as the plaintext of text frames (the frame codec handles text and binary alike), so `recording.state`, `consent.revoked`, `stop.sharing`, `voice.state` and `agent.stats` cannot be read or forged by the signaling server. `ia.sec` carries the plaintext JSON handshake below and nothing else. Nothing is sent on an encrypted channel before state `established`; the console shows "Securing the connection" meanwhile and greys every control. **Channel lifetime rule:** a close of any `SEC_ENCRYPTED_LABELS` channel while its peer connection is alive, a data channel opened by the **remote** side (`ondatachannel`) with any label in `P3_DATA_CHANNEL_LABELS`, or any eighth channel, is `sec.fail { reason: 'channel' }` (the stray channel is closed unread) and triggers the §3.7 rebuild with fresh keys; channels are never re-created on a live peer connection, so a `seq` never restarts under a key.

| Step | Who | Message / rule |
|---|---|---|
| 1 | both | On `ia.sec` open each side generates an ephemeral X25519 key pair (`esk`, `epk`) and reads **both** DTLS fingerprints from the descriptions, the same way on both sides: own `fpr` = the `a=fingerprint:sha-256` line of `currentLocalDescription` (session level, else the first media level), remote = the same line of `currentRemoteDescription`, each normalised to 64 lower-case hex chars without colons. The console may cross-check its own value against `pc.getStats()` (`certificate` referenced by the `transport`'s `localCertificateId`, Chromium only) but never depends on it; webrtc-rs reads the same lines from its local and remote descriptions |
| 2a | both | **Commit first:** send `{ t: 'sec.commit', v: 1, sessionId, side: 'desk' \| 'assist', h: base64url(sha256(utf8(canonicalJson({ side, suite, epk, fpr })))), gen, ts }` where `gen` is the key generation of this peer connection (0 for the first PC of the session, +1 per §3.7 rebuild or hand-over, carried in the §3.7 `webrtc.offer { restart: true, gen }`). A second `sec.commit` from the same side, a wrong `sessionId`, `side` or `gen` answers `sec.fail` |
| 2b | both | **Hello only after the peer's commit is held:** send `{ t: 'sec.hello', v: 1, sessionId, side, suite: 'x25519-xchacha20poly1305-hkdfsha256', epk: base64url(32 bytes), fpr, ts }`. A `sec.hello` received before its sender's `sec.commit`, a second `sec.hello` from the same side, an unknown `suite`, a wrong `sessionId` or a wrong `side` answers `sec.fail` |
| 3a | both | verify `sha256(utf8(canonicalJson({ side: peer.side, suite: peer.suite, epk: peer.epk, fpr: peer.fpr })))` equals the committed `peer.h` (constant-time); mismatch => `sec.fail { reason: 'commit' }`. With the commit a man in the middle must choose its `epk` towards a side before seeing that side's `epk`, so it gets exactly one SAS guess per leg (1e-6) |
| 3b | both | check `peer.fpr === observedRemoteFingerprint` (constant-time); mismatch => `{ t: 'sec.fail', reason: 'fingerprint', ts }` and teardown (row 9) |
| 4 | both | `ss = X25519(esk, peer.epk)` (an all-zero `ss` => `sec.fail { reason: 'key' }`); `T = sha256(utf8(canonicalJson({ v: 1, sessionId, suite, gen, desk: { h, epk, fpr }, assist: { h, epk, fpr } })))` (A §5.1 canonical JSON; `h` and `epk` as the base64url strings sent, so both commits are in the transcript) |
| 5 | both | `prk = HKDF-Extract(salt = T, ikm = ss)`; `kD2A = HKDF-Expand(prk, "ia-sec-v1 desk->assist", 32)`; `kA2D = HKDF-Expand(prk, "ia-sec-v1 assist->desk", 32)`; `kConf = HKDF-Expand(prk, "ia-sec-v1 confirm", 32)`; `sas = (u32be(HKDF-Expand(prk, "ia-sec-v1 sas", 4)) mod 1000000)` zero-padded to 6 digits, displayed as `483 920` |
| 6 | both | send `{ t: 'sec.confirm', mac: base64url(HMAC-SHA256(kConf, utf8(side) \|\| T)), ts }` where `side` is the sender's own side; verify the peer's `mac` constant-time (`sec.fail { reason: 'mac' }` otherwise). State `established` once both the own confirm was sent and the peer's verified; `esk`, `ss`, `prk` are zeroised |
| 7 | both | the Desk pill **face** (§3.5, beside the timer, always visible, not only in the panel) and the console header show "Security code <sas>"; the console tooltip and the Desk consent receipt say "If the two codes differ, stop the session". **Console gate (default on, org `policy.requireSasConfirm`):** the console's transition to `control` or `elevated` (not `view`) is blocked behind a one-time "Confirm security code" step per key generation in which the technician types the six digits the user reads out; the console compares locally (constant-time, 3 attempts then the step re-arms after 10 s) and on success sends `POST events sec.verified { sas, gen }` (actor user) so the chain records that verification happened. After any rebuild (new `gen`) the console drops itself to `view` (locally: input ops are not sent; the server level is unchanged) and shows a **modal**, not a live-region whisper, until the new code is confirmed. With `requireSasConfirm: false` the step is shown but skippable (**Skip** is chained as `sec.verified { sas: null, gen, skipped: true }`). The Desk receipt and the console session view list every SAS of the session by `gen`. The user is never asked to type anything: the Desk only reads the code out |
| 8 | both | 10 s (`LIMITS.secHandshakeTimeoutMs`) from `ia.sec` open without `established` => `sec.fail { reason: 'timeout' }` |
| 9 | both | on any `sec.fail` (sent or received) or any frame that fails to decrypt or breaks the sequence rule: both sides write `sec.failed` (§3.8), then A hard rule 2 teardown, then WS `session.end` with `note: 'sec:<reason>'`; the api records `endReason: 'error'` for a `session.end` whose note starts with `sec:` **from either side** (Desk or Assist; the Desk's `session.end` normally yields `desk_stopped` and the Assist's `assist_ended`, W21), and the second `session.end` for a session that already ended is answered with a re-sent `session.ended` (idempotent), not `bad_state`, so the race between the two senders changes nothing |
| 10 | both | a peer-connection rebuild (`webrtc.offer { restart: true, gen }`, B §3.5, also after hand-over §7) re-runs steps 1-8 with fresh keys and `gen + 1`; the old keys are zeroised when the old PC closes; `seq` counters belong to a key generation and are never reset or reused under it |

`sec.fail.reason` (`SEC_FAIL_REASONS`): `suite`, `commit`, `fingerprint`, `key`, `mac`, `timeout`, `replay`, `decrypt`, `oversize`, `channel`.

**Frame format on an encrypted channel** (shared `agent/sec.ts`: `encodeSecFrame`, `decodeSecFrame`, `SecChannel`; Rust `ia_core::sec`; Kotlin `SecChannel`):

| Bytes | Field |
|---|---|
| `[0]` | version `1` |
| `[1]` | flags: bit 0 = plaintext is UTF-8 JSON text (0 = binary, e.g. a file chunk of A §8.3); bits 1-7 reserved `0` |
| `[2,10)` | uint64 BE `seq`, per channel per direction per key generation, starts at `0`, +1 per frame |
| `[10,n)` | XChaCha20-Poly1305 ciphertext = plaintext `\|\|` 16-byte tag |

Key = `kD2A` for Desk->Assist frames, `kA2D` for Assist->Desk. Nonce (24 bytes) = `labelId (1 byte: ia.control 1, ia.file 2, ia.playbook 3, ia.chat 4, ia.annot 5, ia.ctrl 6) \|\| direction (1 byte: 0 Desk->Assist, 1 Assist->Desk) \|\| uint16 BE gen \|\| 12 zero bytes \|\| uint64 BE seq` (`gen` is also in `T`, so a key is never shared across generations; the nonce field is defence in depth). AAD = `utf8("ia-sec-v1") \|\| utf8(sessionId) \|\| 0x00 \|\| utf8(label) \|\| 0x00 \|\| version byte \|\| flags byte`. Receiver rule: `seq` must equal `lastSeq + 1` (channels are ordered and reliable; any other value is `sec.fail { reason: 'replay' }`); plaintext length `<= LIMITS.secFrameMaxBytes - 26` (131072 - 26) else `oversize`. **Message-size interop:** the agent calls webrtc-rs `SettingEngine::set_sctp_max_message_size(131072)` so its SDP carries `a=max-message-size:131072` (the Android host sets the same through `PeerConnectionFactory` options), and the console never sends a frame above the remote's advertised size; the largest P3 frame is a `playbook.run` op with a 64 KiB body (§8.4), which fits with its JSON escaping and the envelope. A `SecChannel` constructed for a key generation refuses to start at `seq 0` twice (shared test). The A §8.3 binary chunk codec (`encodeFileChunk`) is unchanged and travels as the plaintext of a binary frame; the A §8.3 JSON messages travel as text frames. `parseDataChannelMessage(label, text, expectedFrom)` is applied to the decrypted text exactly as before.

## 2. Token and download flow for P3

Tokens are unchanged (A §3): tier `p3_portable`, `typ` `one_time` or `timed`, seat tier cap applies, `PublicToken.joinSupported` becomes `true` for `p3_portable` (§13.3). The Android host joins on the same `p3_portable` token (PRD 4 row "Mobile support": Android host app at P3; W10).

### 2.1 How the token reaches the agent (carriers and precedence)

| Rank | Carrier (`TokenSource`) | Mechanics | Why this rank |
|---|---|---|---|
| 1 | `arg` / `deeplink` | `IndiansAssist.exe --code <compact or 12 digits>` or `indiansassist://join?t=<compact>` (`c=<12 digits>` also accepted; `--url` takes the **entire remaining command-line tail** as the URL and every other switch is ignored, §2.5 L2). A second instance forwards its argument to the running one over the single-instance pipe `\\.\pipe\IndiansAssist.<userSid>.<logonRand>` (§11.5, squatting-safe client and server rules there) and exits. The running instance honours a forwarded code **only** in the connect / idle state; while `waiting`, `consent_pending` or `active` it shows "Another support code was received; finish this session first" and discards it (a local URL open can neither swap the token nor end a live session) | explicit user action, freshest |
| 2 | `sidecar` | a **signed** `<exe stem>.iaconfig` next to a filename-carried exe, or `IndiansAssist.iaconfig` next to an exe named exactly `IndiansAssist.exe` (§2.4); consumed (shredded and deleted) as soon as it is parsed | placed deliberately by a technician or a self-host deployment, and signed by the region's key |
| 3 | `filename` | the exe's own name carries the region and a 12-digit **desk code** minted for this download (§2.3; never the dashboard's short code and never the compact token) | survives the download unchanged; came with this exact download; dies when the first session on the token reaches `active` |
| 4 | `clipboard` | read **once** at first start (`arboard`, text only); accepted only when `normaliseTokenInput(text)` is not `null`; the window says "We found a support code on your clipboard" and names the source; the agent never writes clipboard **content**, with one reasoned exception: having read a token or code from the clipboard it clears that one entry (`EmptyClipboard` while the current text still equals what it read) so the credential does not stay in Clipboard History (PRD 6 fast path; W5) | convenient, overwritable, readable by every app |
| 5 | `manual` | field "Paste your support code or link" accepting the 12-digit code, the compact token or a full `/join#t=` URL (A §3.3 algorithm, copied into `ia_core::join_input`) | fallback |

Rules: the first rank that yields a value wins; lower ranks are not read (the clipboard is read only when ranks 1-3 yield nothing). The chosen source is shown in the connect window and sent as `desk.hello.client.tokenSource` (§3.1) so the dashboard can show which path Desks actually use. A compact token is verified locally before any network call: fetch `${apiOrigin}/.well-known/indiansassist.json` (cached in memory for the process lifetime), run `checkToken` (A §3.4-3.5 client subset: parse, signature, `iat`/`exp`); failure shows "This code is not valid" and falls through to manual entry. A 12-digit code (a dashboard short code typed or pasted, or a desk code from the filename) is Luhn-checked locally (`isValidShortCode`), then resolved by `POST /api/v1/tokens/public-lookup { code }` (headers `X-Requested-With: IndiansAssist`, no `Origin`, no cookie; A §6.1 accepts an absent `Origin`); the server resolves a **desk code** (§2.2) only for a request without `Origin` (native client) and otherwise treats it as an unknown short code (S2 rules). `apiOrigin` comes from, in order: `--api-origin` (compiled only into dev builds behind `#[cfg(feature = "dev")]`; a release build has no such switch, so it is not a convention but a compile-time guarantee), the signed sidecar (§2.4 rule), the filename region mapped through the compiled `IA_REGION_ORIGINS`, the compiled `IA_API_ORIGIN` default. A `421 region_mismatch` with `details.origin` is followed once when `origin` is in the compiled list (A R3).

The dashboard short code is never written to disk by this flow |
| `GET /api/v1/download/:grant` (and `HEAD`) | none | optional `Range` | the grant is **not** single-request (browsers, SmartScreen and download managers issue several GETs per download): each `GET` atomically increments `uses` (`Presence.incr`, `ia:dl:<hash>:uses`, same TTL) and is refused with `410 link_expired` above `LIMITS.downloadGrantMaxUses` (3); the client IP must equal the `prepare` IP (else `410`); `HEAD` is free and uncounted; `Accept-Ranges: bytes` and `Range` are honoured (`206`); `entry.region` must be in this node's `SERVED_REGIONS` (else `410`, never served cross-region); missing or expired => `410 link_expired`; the entry dies with its TTL (no compare-and-delete). Streams `AGENT_DIST_DIR/<file>` with `Content-Type: application/vnd.microsoft.portable-executable` (`application/vnd.android.package-archive` for Android), `Content-Length`, `Content-Disposition: attachment; filename="<§2.3 name>"` (Android: the dist name `IndiansAssist-android-universal-<version>.apk`; the app ignores its own filename), `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, `Content-Security-Policy: sandbox; default-src 'none'`; audit `download.served { tokenId, platform, arch, version, sha256 }` **once per grant** (on the first `200`/`206`; actor `system`, `session_id` null). nginx `client_max_body_size` is irrelevant (download); `proxy_buffering off` for this location |

`AGENT_DIST_DIR` (default `./data/agent-dist`, git-ignored) holds `manifest.json` and the files it names (`IndiansAssist-windows-x64-<version>.exe`, `IndiansAssist-windows-arm64-<version>.exe`, `IndiansAssist-android-universal-<version>.apk`). CI publishes them; a node without the directory answers `503 download_unavailable` on `prepare` and `builds: []` on the manifest, and the join page then shows the §2.7 "not available on this server" text. The grant, desk-code and hand-over stores follow `PRESENCE_DRIVER` (memory per process, Valkey cluster-wide) so a multi-node region serves the GET on any node. `Presence` (`apps/api/src/adapters/presence.ts`) gains two atomic primitives both drivers implement and `test/presence.test.ts` races with two concurrent callers: `consume(key): Promise<string | null>` (Valkey `GETDEL`, or `EVAL` of `local v = redis.call('GET', KEYS[1]); if v then redis.call('DEL', KEYS[1]) end; return v` below 6.2; memory: `Map.get` + `Map.delete`), used by the hand-over token (§7.2) so exactly one of two racing consumers wins, and `incr(key, ttlSeconds): Promise<number>` (`INCR` + `EXPIRE NX`; memory counter with expiry), used by the download grant. `get`-then-`del` is never used for anything single-use.

### 2.3 Stub identity: the filename carrier (binding) and the rejected trailer

**Binding:** the served filename is `IndiansAssist-<region>-<dddd>-<dddd>-<dddd>.exe`, e.g. `IndiansAssist-in-mum-4821-9365-7715.exe`; the 12 digits are the **desk code** minted by `prepare` for this download (§2.2), **not** the token's short code (`token.short_code`, A §3.3) and not the compact token, and `<region>` is the token's `reg`. The agent parses `std::env::current_exe()`'s file name with `^IndiansAssist-(?<region>[a-z]{2}-[a-z]{3,5})-(?<a>\d{4})-(?<b>\d{4})-(?<c>\d{4})(?: \(\d+\))?\.exe$` (case-insensitive; the ` (1)` suffix a browser adds to a duplicate download is tolerated), requires `region` to be in the compiled `IA_REGION_ORIGINS` list and the 12 digits to be Luhn-valid, and uses them as rank 3 of §2.1. **Why a desk code:** a filename is written to disk in cleartext and read by Explorer, Windows Search, Recent Items, browser download history, cloud Downloads backup and AV telemetry; the dashboard short code is a join credential for the token's whole life (up to 8 h for `timed`, A S4 treats it as sensitive), so it never goes on disk. The desk code is accepted only by `desk.hello` from `client.kind === 'native'` and by `public-lookup` without `Origin`, resolves to the token through `ia:dc:` (same S2/S3 failure rules and budgets as a short code; every miss is `token_not_found`), and is deleted when the first session on the token reaches `active`. Residual (§14): until that moment anyone who reads the filename on the Desk can join as that Desk; the knock still needs the technician's accept, and the Desk that is already waiting makes the second one `token_busy`.

**Rejected: an appended config trailer.** Authenticode hashes every byte of a PE except the checksum field, the security data directory entry and the certificate table itself; bytes appended after the certificate table are hashed, so a per-download trailer invalidates the CI signature and the stub would show "Unknown publisher" on every Desk. Hiding the config inside the certificate table padding is the technique Microsoft's opt-in `EnableCertPaddingCheck` rejects and is excluded. The task's trailer option is therefore not implemented (W1); the sidecar of §2.4 is the configurable path, the filename the default path, and the signed exe is byte-identical for every download (cacheable, verifiable against `manifest.sha256`).

### 2.4 Sidecar `.iaconfig` (optional)

A UTF-8 JSON file (`<= LIMITS.iaconfigMaxBytes` = 16384) next to the exe, strict shape (`iaconfigSchema`, shared `agent/download.ts`; unknown keys are an error), **signed** by the region's token-signing key:

```json
{ "v": 1, "apiOrigin": "https://in.indiansassist.example", "region": "in-mum", "code": "ia1.3f9a...", "deskLabel": "Rahul", "kid": "3f9a1c2b4d5e6f70", "sig": "<base64url Ed25519 over canonicalJson(sidecar minus sig)>" }
```

**Which file is honoured:** for an exe whose name matches the §2.3 grammar, only `<exe stem>.iaconfig` (e.g. `IndiansAssist-in-mum-4821-9365-7715.iaconfig`); the generic `IndiansAssist.iaconfig` is honoured **only** next to an exe named exactly `IndiansAssist.exe` (the D5 Keep copy or an MSP-renamed stub). A planted generic file in Downloads therefore never applies to later legitimate downloads. The agent parses the sidecar once, then immediately overwrites it with zeros and deletes it (it has consumed it; the receipt notes "configuration file used and removed"), so a crash never leaves a token on disk.

| Field | Rule |
|---|---|
| `v` | `1` |
| `apiOrigin` | `https:` origin, no path; `http://localhost:*` / `http://127.0.0.1:*` only in a dev build (`IA_DEV=1`). A **release** build refuses a sidecar whose `apiOrigin` is outside the compiled `IA_REGION_ORIGINS` unless `sig` verifies (below); a self-hoster builds with their own origins and keys compiled in and signs sidecars from their own dashboard. A **dev** build accepts a foreign origin and shows the yellow line "Connecting to <host>, a server not operated by IndiansAssist" on the connect and consent windows |
| `region` | `Region`; must equal the token's `reg` after verification (else "This code belongs to another region") |
| `code` | compact token or 12 digits, optional (a sidecar may carry only the origin for a self-host deployment: ranks 3-5 then supply the code). When the sidecar `code` and the filename code (§2.3) disagree, the **filename wins** and the connect window says "The configuration file named a different code; using the one from the download" |
| `deskLabel` | optional, `<= 80`, pre-fills "Your name" |
| `kid`, `sig` | **required.** `sig` = Ed25519 (`ed25519-dalek`) over `utf8(canonicalJson(sidecar minus sig))` by the region's token-signing key `kid` (the dashboard holds it: it is the key that signs tokens). The agent verifies against the **compiled** region key set `IA_REGION_PUBKEYS` (current and previous keys per region, generated into the build by CI from each region's well-known; a self-hoster's build carries theirs); a `kid` not in the compiled set, or a bad signature, is "This configuration file is not signed by a known server" and the sidecar is ignored (ranks 3-5 continue). The earlier `pubkeys` pin is dropped: whoever writes a hostile origin writes matching pins, so it defended nothing |

The sidecar is consumed on parse (above) and, if still present, deleted with the exe on self delete (§10). Generating a sidecar is a dashboard feature of the tokens page ("Download .iaconfig for this token", org_admin and the creator; the api signs it: `POST /api/v1/tokens/:id/iaconfig` -> `200 { iaconfig: string }`, same roles, audit `token.iaconfig_issued { tokenId }`) so an MSP can ship exe + sidecar through its own tooling (PRD 4 "Portable push").

### 3.7 Resume and peer-connection rebuild

For `client.kind === 'native'` the B Y2 extension rule applies: a Desk resume from `active` keeps `active`; the server re-sends `session.created` (real state) to the Desk, then `ice.refresh`, and `desk.reconnected { state: 'active', consentState: 'granted' }` to the Assist. ### 4.3 Adaptive bitrate, ladders and floor mode

Controller (`ia-core::abr`, platform-free, unit-tested against `fixtures/agent/abr.json`): webrtc-rs ships no congestion-control estimator (its `interceptor` crate has `nack`, `report`, `twcc` and `stats`, no port of pion's `cc`), so the estimator is ours. Inputs: **REMB** (`ReceiverEstimatedMaximumBitrate` parsed from `RTCRtpSender::read_rtcp()`, polled on a dedicated tokio task so the RTCP channel never backs up; Chrome sends it for `goog-remb`) is the primary estimate; `fraction_lost` and RTT from receiver reports; **TWCC** feedback (`TransportLayerCc`, read from the same RTCP stream when the Assist negotiated `transport-cc`) is consumed by `ia_core::abr::twcc`, a delay-gradient estimator: inter-arrival delta trend over 20-packet windows, `+8 %` per window with a falling or flat trend, `-8 %` per window with a rising trend, clamped to `[0.5, 1.5] x remb` when REMB is present; and the capture fps. Rules: target = `min(remb, twccEstimate)` smoothed over 2 s; loss `> 10 %` for 2 s => target x 0.7; loss `< 2 %` for 5 s => target x 1.08 (cap `LIMITS.agentMaxKbps` = 6000 per selected monitor, 8000 total **including the recorder stream**, §9 R2); the rung is the highest whose `minKbps <= target`; a rung change forces a keyframe; hysteresis 3 s up, 1 s down.

| Rung | Target kbps | Long edge max (px) | fps max | Encoder tuning |
|---|---|---|---|---|
| `full` | `>= 2500` | native up to 2560 | 30 | default |
| `high` | 1500-2500 | 1920 | 24 | default |
| `medium` | 800-1500 | 1600 | 15 | screen-content |
| `low` | 300-800 | 1280 | 10 | screen-content, min quantiser raised |
| `floor` | `< 300` (PRD 13 "sub 300 kbps floor mode", PRD 12.11) | 1024 | 5 | screen-content, keyframe interval 15 s, dirty-rect only, cursor still composited, **session budget** 250 kbps hard cap for the whole Assist leg: in floor (auto or forced) at most **one** monitor streams (the first selected; the others are paused and the mosaic shows them as "Paused, low bandwidth" thumbnails), `floorMode: true` in stats, console banner "Low bandwidth mode" |

Manual override: `os.quality { preset: 'auto' \| 'sharp' \| 'smooth' \| 'floor' }` (`QUALITY_PRESETS`, `view` level): `sharp` pins the long edge to native and lets fps drop first; `smooth` pins fps to 30 and lets resolution drop first; `floor` forces the floor rung; `auto` (default) is the controller. The Android host implements the same ladder through libwebrtc's `RtpParameters` encodings (`maxBitrateBps`, `scaleResolutionDownBy`, `maxFramerate`). **Recorder stream and the floor (honest, W24):** the recorder stream follows `min(assistRung, medium)` (so in floor it is also capped at 250 kbps and 5 fps) and shares the Assist encoder whenever the codecs match (§4.2); the Desk **uplink** in floor mode with a server recorder is therefore up to 2 x 250 kbps (one encode, two receivers), and the PRD 13 "sub 300 kbps" figure holds per leg, not per uplink, when a server recorder is assigned. The ABR unit tests cover rung transitions, floor with 1 and 3 selected monitors, and the recorder rung.

### 4.4 Stats

The agent sends `{ t: 'agent.stats', encoder: VideoEncoder, hwEncoder: boolean, capturePath: 'dda' \| 'gdi' \| 'projection', rung: ('full' \| 'high' \| 'medium' \| 'low' \| 'floor') \| null, floorMode: boolean, targetKbps: int, sentKbps: int (summed over the Assist and recorder PCs), recorderKbps: int \| null, captureFps: number, sentFps: number, encodeMs: number \| null (average capture-to-encoded latency over the interval), monitors: [{ id, width, height, fps }], cpuPercent: number \| null, ts }` on `ia.ctrl` every 2 s (`LIMITS.agentStatsIntervalMs`); `capturePath: 'projection'` and `rung: null` are what the Android host sends (MediaProjection has neither DDA/GDI nor an exact rung; `ctl.event capture.path` gains `projection` likewise). ### 5.2 Console capture of input

The `RemoteView` canvas gets a transparent overlay (`tabindex=0`): pointer events become `os.pointer` with `monitorId` from the hit monitor (single view: the viewed monitor; mosaic: the tile), `nx`/`ny` relative to that monitor's rendered rect; `wheel` becomes `os.scroll` at the pointer; `keydown`/`keyup` become `os.key` when `event.key.length > 1` (named keys: `Enter`, `Backspace`, `Tab`, `Escape`, arrows, `F1`-`F24`, `Delete`, `Home`...), when `ctrl`, `alt` or `meta` is held, or when `code` starts with `Numpad`; otherwise printable characters are buffered and flushed as one `os.text` every 50 ms or 32 characters (`beforeinput` / `keypress` `data`, so dead keys and IME composition on the technician's side produce the composed text). `preventDefault` on everything while the overlay has focus, except `F11`, `Escape` held for 1 s (releases the overlay) and the browser's own `Ctrl+Shift+Tab` family which the page cannot intercept. Modifier state: the console sends `os.key down`/`up` for `ControlLeft`, `ShiftLeft`, `AltLeft`, `MetaLeft` and their right variants as they happen and sets `modifiers` on every op for the agent's cross-check; on overlay blur the console sends `up` for every modifier it believes is down.

### 5.3 Pointer mapping (`ia-input-win`)

`monitor = monitors[monitorId]` (else `no_such_monitor`); `px = monitor.x + nx * monitor.width`, `py = monitor.y + ny * monitor.height` in virtual-desktop pixels (physical, DPI-unaware process: the agent is `PROCESS_PER_MONITOR_DPI_AWARE_V2` so `EnumDisplayMonitors` returns physical rects); `SendInput` with `MOUSEEVENTF_MOVE | MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`, `dx = round((px - vx) * 65535 / vw)`, `dy = round((py - vy) * 65535 / vh)` over the virtual screen rect (`SM_XVIRTUALSCREEN`..); `down`/`up`/`click` map to `MOUSEEVENTF_{LEFT,MIDDLE,RIGHT}{DOWN,UP}` and `MOUSEEVENTF_X{DOWN,UP}` with `XBUTTON1/2`; `dblclick` = two clicks within `GetDoubleClickTime()`; `os.scroll` = move then `MOUSEEVENTF_WHEEL` (`mouseData = -dy * WHEEL_DELTA`) and `MOUSEEVENTF_HWHEEL` (`dx * WHEEL_DELTA`). Every injected pointer and keyboard event is tagged `dwExtraInfo = 0x49415F31` ("IA_1") so the agent's own `WH_MOUSE_LL` / `WH_KEYBOARD_LL` hooks (§3.5 self-defence: they drop tagged events aimed at the agent's own windows) and future Phase D code can tell injected from real input.

### 5.4 Keyboard mapping

### 5.5 UIPI and the secure desktop (honest limits)

A medium-integrity agent cannot inject input into a window of a higher integrity level (UIPI): `SendInput` returns 0 with `ERROR_ACCESS_DENIED`. The agent reports `blocked_uipi` on the op and `ctl.event input_blocked { cause: 'uipi' }` (at most one per 5 s); the console shows "This window runs as administrator; request elevation to control it" with a button that opens the §7 dialog. While the secure desktop is active nothing can be injected or captured (§4.1); ops answer `secure_desktop`. Both limits end for elevated windows after hand-over (§7); the secure desktop stays out of reach until the Phase D service.

## 7. Just-in-time elevation (PRD 12.4)

### 7.1 Model (binding: relaunch and hand-over)

The agent runs at the user's integrity level. When the technician needs administrator rights, the agent relaunches an **elevated helper** (the same exe, `runas` verb) that connects to the **same session** as the Desk and takes it over; the first (user) instance then exits. The rejected alternative (the elevated process joins as a second participant) is W8: two Desk peers would double the capture bandwidth, split input between two integrity levels and need a second consent and recorder negotiation; one elevated Desk that replaces the first is simpler and matches the A resume machinery. Hand-over is bound by a one-time token the API mints (§7.2), so a local process cannot seize a session by guessing its id.

### 7.2 Hand-over token

| Message / path | Dir | Request | Response |
|---|---|---|---|
| control op `elevation.request { reason }` on `ia.control` (§5.1) | A->D | the console asks | the agent, on the Desk's Allow, requests the token with `desk.elevation { sessionId, opId }` |
| `desk.elevation { sessionId, opId }` (new D->S, `active` only, level `control`, `session.tier === 'p3_portable'`, the Desk's `desk_client.capabilities.features` must contain `elevation` and `os === 'windows'`, else `error bad_state`) | D->S | | reply `elevation.handover { sessionId, handover, expiresAt }` (new S->D): `handover` = 32 CSPRNG bytes base64url; the server stores `ia:ho:<sha256Hex(handover)>` = `{ sessionId, tokenId, orgId, region, assistUserId, opId, expiresAt }` with TTL `LIMITS.handoverTtlSec` (120) **and** persists `session.handover_hash`, `session.handover_opid`, `session.handover_expires_at` on the row (the store alone cannot drive the sweeper: an expired key simply vanishes). **One outstanding hand-over per session:** a new `desk.elevation` deletes the previous key and overwrites the row fields; at most 3 mints per session per 10 minutes (`error rate_limited`). Audit `elevation.handover_minted { opId, expiresAt }` (actor desk, written by the server) so a modified agent minting hand-overs leaves a trace; the console already wrote `elevation.requested` through `POST events` |
| `desk.hello { token, handover, client }` | D->S | the elevated instance connects a fresh socket | **Order in `handleDeskHello` (binding):** (1) A §3.5 steps 1-6 and 8 on `token`; step 7 is run with the **hand-over relaxation** (amends A §3.5 and A §7.5, §16.1): `status = used` is accepted when `handover` is present and `sha256Hex(handover)` equals `session.handover_hash` of a non-ended session on this token, and the A §7.5 `token_busy` check is **skipped** for such a hello (the hand-over replaces the live Desk; a `one_time` token is `used` from the first `active`, so without this relaxation elevation could never complete). **Parent -> child transport (binding).** `ShellExecuteExW` with `runas` creates the elevated child through AppInfo, not through the parent, so no handle, stdin or anonymous pipe can be inherited; the parent therefore opens a **named** pipe `\\.\pipe\IndiansAssist.ho.<32 random hex>` **before** launching (`FILE_FLAG_FIRST_PIPE_INSTANCE | PIPE_REJECT_REMOTE_CLIENTS`, one instance, DACL granting the current user SID and `BUILTIN\Administrators`, creation failure aborts the elevation with `launch_failed`) and passes only the suffix on the child's command line (`--handover-pipe <hex>`; the suffix is not secret, the pipe's authenticity checks are). The parent accepts exactly one client within 20 s and, before writing, verifies that `GetNamedPipeClientProcessId` equals the pid of the process `ShellExecuteExW` returned (`SEE_MASK_NOCLOSEPROCESS`, `GetProcessId(hProcess)`) and that `QueryFullProcessImageNameW` of that process equals the parent's own image path; any other client is disconnected and the elevation fails `launch_failed`. It then writes one JSON blob `{ v: 1, handover, token, apiOrigin, signalUrl, sessionId, imageSha256, tokenSource, deskLabel, consent: { level, monitors, clipboard } }` (the child inherits the consent choices and reports the parent's `tokenSource`) and closes the pipe. The child opens the pipe with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` (never impersonation), verifies `GetNamedPipeServerProcessId` is its parent pid (`NtQueryInformationProcess` / `CreateToolhelp32Snapshot` parent) with the same image path, reads the blob, zeroises the buffer, and connects. The blob never touches disk, the environment or the command line.

### 7.3 Sequence

1. Console: `elevation.request { reason }` on `ia.control`; console `POST events elevation.requested { opId }` with the reason.
2. Agent: indicator prompt card "<technician> needs administrator rights to: <reason>. Windows will ask you to confirm." **Allow** / **Refuse**, 60 s. Refuse / timeout => `desk.event elevation.denied { opId, cause }`, `ctl.event elevation { state: 'denied' }`. The op's `{ accepted: true }` returned at once; the outcome is event-driven.
3. On Allow (a **physical** click, §3.5): `desk.elevation` -> `elevation.handover`; the parent opens its own exe with `GENERIC_READ` and **`FILE_SHARE_READ` only** and holds that handle through the UAC prompt (a swap-by-replace of the file in the user-writable Downloads folder is thereby blocked; a swap-by-rename is caught by the child's hash check), runs `WinVerifyTrust` plus the `IA_EXPECTED_SIGNER` subject compare on that handle (dev builds: `TRUST_E_NOSIGNATURE` tolerated) and computes `imageSha256` over it; creates the §7.2 named pipe; the prompt card now also says "In the Windows dialog, check that the publisher reads **<IA_EXPECTED_SIGNER>** and cancel otherwise"; `ctl.event elevation { state: 'uac_shown' }`; relaunch elevated with `ShellExecuteExW({ lpVerb: 'runas', lpFile: <current exe>, lpParameters: '--handover-pipe <hex>', fMask: SEE_MASK_NOCLOSEPROCESS })`. A cancelled UAC prompt (`ERROR_CANCELLED` 1223) => `elevation.denied { cause: 'uac_cancelled' }` and the user instance stays in control; other `ShellExecuteExW` failure => `elevation.failed { error: 'launch_failed' }`. With UAC disabled and the user already elevated, `runas` is skipped and the hand-over socket connects directly.
4. Elevated child: reads the blob (§7.2), hashes its own `current_exe` and refuses with `elevation.failed { error: 'image_mismatch' }` (reported by the parent, which also keeps the session) when the hash differs from `imageSha256` or the signer is not the compiled `IA_EXPECTED_SIGNER` (§2.6: fatal in the child); refuses to start (same error) if `GetModuleFileNameW` of any loaded module lies outside `%SystemRoot%` or its own image (§14 DLL rule); then `desk.hello { token, handover, client }` with `client.elevation = 'admin'`, keeps the `resumeKey` from `desk.hello.ok`, and on `session.created` rebuilds capture, tracks, channels and the §1.3 handshake with `gen + 1` (§3.7 rebuild, new security code; the console re-confirms it); `ctl.event elevation { state: 'handover' }`.
5. User instance: on `session.handed_over` / close `4411` (§7.2) **or** on the child's success message over the hand-over pipe (whichever arrives first) it runs hard rule 2 **without** `session.end` (the session continues on the child), removes its pill and exits; the child re-asserts the HKCU handler. Any other close code keeps the §3.1 reconnect behaviour. If neither signal arrives within 20 s the user instance keeps the session and writes `elevation.failed { error: 'connect_failed' }`; a child that then connects late is rejected by the server (its hand-over was consumed or expired) and exits.
6. The elevated instance now injects into elevated windows (UIPI lifted for its integrity level) and runs `requiresElevation` playbooks as administrator; playbooks without `requiresElevation` still run as the **user** (limited linked token, §8.4). The pill shows the shield glyph; the console chip shows "Elevated".

### 7.4 What elevation unlocks and what it does not (honest)

| Unlocked by hand-over | Still impossible in Phase C (needs the Phase D service) |
|---|---|
| Input into windows running as administrator (same-integrity injection no longer blocked by UIPI) | Capturing or clicking the **UAC secure desktop** itself (consent.exe runs on a separate desktop a user process cannot read; §4.1, §5.5) |
| Reading/writing system-protected locations through playbooks | The **lock screen**, Winlogon and Ctrl+Alt+Del desktop |
| `requiresElevation` playbooks (§8) | Surviving logoff/reboot, pre-login access (no service) |
| Diagnostics needing admin (event logs, `sfc`, service restarts) via playbooks | `os.input_lock` / `os.privacy_screen` (defined, answer `not_supported { message: 'phase_d' }`) |

When elevation is active the console states: "Administrator windows can now be controlled. Windows' own security prompts (UAC, the lock screen) still cannot be seen or clicked; ask the user to complete those." (P8).

**Honest limit of UAC over a user-writable binary (P8).** The exe elevates from wherever the browser saved it, a folder every same-user process can write. The §7.3 handle hold, the signer check on that handle, the image hash the child verifies, the fatal signer check in the child, the §14 import-table rule and the UAC dialog's publisher line are what the product can do; a user who clicks **Yes** on a UAC prompt whose publisher is not `IA_EXPECTED_SIGNER` has elevated something else, and Windows offers no stronger guarantee for a portable binary than that. The Phase D installed agent (program files, service) removes this class.

### 7.5 Audit

`elevation.requested` (user, `{ opId }`, reason column), `elevation.granted` (desk, `{ opId, elevation: 'admin' }`), `elevation.denied` (desk, `{ opId, cause }`, reason column), `elevation.failed` (desk/system, `{ opId, error }`). `elevation.requested` was a reserved A name, now written; `session.supervisor_joined` stays reserved.

## 8. Playbooks (PRD 12.6)

### 8.1 Catalogue model

A playbook is an org-scoped, pre-approved script. It runs only when the body's sha256 matches the catalogue the server delivered at session start (§8.3). Playbooks are the **audited, pre-approved** way to run scripts (P6): the pin guarantees that what ran is what the org approved and what the chain says; it is not a claim that a technician at `control` cannot run arbitrary code by other means (they can type it), and the server recording plus `input.text_burst` (§3.8) are the compensating record. The dashboard copy recommends `recordingMode: server` for orgs that use P3.

Table `playbook` (migration `0005_phase_c`): `id` uuid pk; `org_id` fk org, index; `name` text (1..80, sanitised); `description` text (<= 500, sanitised); `interpreter` pgEnum `playbook_interpreter` (`powershell`, `cmd`, `sh`); `body` text (<= `LIMITS.playbookBodyMaxBytes` = 65536); `body_sha256` char(64) computed server-side over UTF-8 `body` (the client never sets it); `requires_elevation` boolean default false; `parameters` jsonb default `[]` (array of `PlaybookParam`, at most `LIMITS.playbookParamsMax` = 16); `timeout_sec` int default 120 (1..`LIMITS.playbookTimeoutMaxSec` = 900); `enabled` boolean default true; `created_by` fk user; `created_at`/`updated_at`; unique `(org_id, name)`. `PlaybookParam = { name: /^[a-z][a-z0-9_]{0,31}$/, label (<= 80), type: 'string'|'int'|'bool'|'enum', required: boolean, default?, enum?: string[] (<= 20, each <= 40), pattern: string (RE2, <= 200, **required** for `type: 'string'`, anchored by the server as `^(?:...)$`, absent for other types), min?, max? (int) }` (`playbookParamSchema`, strict). The admin body editor (§13.4) lints and **warns** on `Invoke-Expression`, `iex`, `Add-Type`, `Start-Process`, `cmd /c` and `%IA_PARAM` in PowerShell bodies, and **refuses** (`400 validation_failed`, `details.lint`) a `cmd` body that references `%IA_PARAM_` anywhere except inside the quoted form `set "x=%IA_PARAM_X%"`.

`PLAYBOOK_INTERPRETERS = ['powershell', 'cmd', 'sh']`; `sh` is Android/Phase E only (the Windows agent answers `not_supported` for `sh` and advertises `interpreters: ['powershell', 'cmd']`).

### 8.2 REST (org management and run)

| Method / path | Roles | Request | Response |
|---|---|---|---|
| `GET /api/v1/orgs/current/playbooks` | any authenticated role | `?enabled=&limit&cursor` | `200 Page<Playbook>` scoped to `p.org.id` (a `cursor` can never page into another org's rows); `body` included for org_admin / senior_technician / auditor and **omitted** for technician and observer (`bodyHash` only). This gating is least exposure in the UI, **not** a security property: the body is disclosed to the running technician at run time by the run endpoint below |
| `POST /api/v1/orgs/current/playbooks` | org_admin | `{ name, description, interpreter, body, requiresElevation?, parameters?, timeoutSec? }` | `201 Playbook`; `body_sha256` computed server-side; audit `playbook.created { playbookId, bodyHash, interpreter, requiresElevation }`; duplicate name => `409 playbook_name_taken` |
| `PATCH /api/v1/orgs/current/playbooks/:id` | org_admin | partial | `200 Playbook`; the row is loaded by `(id, org_id = p.org.id)` else `404 not_found` (A §2.3 convention: another org's id is not a 403); a `body` change recomputes `body_sha256`; audit `playbook.updated { playbookId, fields, bodyHash }` |
| `DELETE /api/v1/orgs/current/playbooks/:id` | org_admin | | `204` (prefer `enabled=false`); same `(id, org_id)` load, else `404`; a hard delete audits `playbook.deleted { playbookId }`. Past `playbook.run` entries keep their `playbookId` and `hash` (the chain is the record) |
| `POST /api/v1/sessions/:id/playbooks/:playbookId/run` | assist of the session (any role that can be the Assist) | `{ args: Record<string, string\|number\|boolean>, reason?: string }` | **This endpoint is the body's release point** (the console path; PRD 11 `POST /devices/:id/script` adapted to a session, W4). Order: `scopedSession(ctx, p, id, { write: true })` + `requireSessionAssist` (another org's or another technician's session => `404` / `403` as A); `session.tier === 'p3_portable'` and `active` (else `409 bad_state`); the playbook is loaded by `(playbookId, org_id = session.org_id)` else `404 not_found`; `enabled` else `409 playbook_disabled`; `body_sha256` must equal the hash in the manifest delivered at this session's `session.created` (kept on `live.playbookManifest`) else `409 playbook_changed` (a body edited mid-session is caught here, never first by the agent's `hash_mismatch`); `requires_elevation` against `session.consent_level === 'elevated'` (else `403 forbidden` code `elevation_required`); `validatePlaybookArgs(parameters, args, interpreter)` (§8.4 rules; `400 validation_failed`). The server mints `runId` = 32 lower-case hex (CSPRNG) and `opId = opIdFor(sessionId, runId)`, writes `playbook.run_requested { playbookId, bodyHash, runId, opId }` (actor user, reason column) and answers `202 { runId, opId, body, bodyHash, interpreter, requiresElevation, timeoutSec, args }` with the body at the moment of the run and the **canonicalised** args. The console copies these fields **verbatim** into the encrypted `playbook.run` op with `ctl.req.id = runId` (§8.4); the REST call is the authenticated attestation, the data-channel op the execution path (two reporters, §3.8). A `technician` can therefore complete a run end to end without ever listing bodies |

`Playbook` wire = `{ id, name, description, interpreter, requiresElevation, parameters, timeoutSec, enabled, bodyHash, body?, createdBy, createdAt, updatedAt }`.

### 8.3 Catalogue delivery at session start

`session.created` for a `p3_portable` session carries `agent?: { playbooks: PlaybookManifest[] }` (both copies; omitted for other tiers); `PlaybookManifest = { id, name, description, interpreter, requiresElevation, parameters, timeoutSec, bodyHash }` (no `body`: the agent gets the body only in the run op and verifies it against this pinned hash). The manifest is the org's `enabled` playbooks the agent's `interpreters` can run, ordered by `updated_at` desc, capped at `LIMITS.playbookCatalogueMax` (100) **and** at `LIMITS.playbookManifestMaxBytes` (32768) of serialised JSON, so `session.created` stays well inside the A §7.1 64 KiB frame; when the cap trims entries the server sets `agent.truncated: true` and the console lists the rest from REST. The server keeps the delivered manifest on the live session (`live.playbookManifest`) for the §8.2 `playbook_changed` check. The agent shows it read-only; the console lists the same.

### 8.4 Run op (on `ia.control`, encrypted; output on `ia.playbook`)

| `op` | `args` | `result` |
|---|---|---|
| `playbook.run` | `{ runId: hex32, playbookId: uuid, bodyHash: hex64, body (<= 65536 UTF-8 bytes), interpreter, args (canonical strings), requiresElevation: boolean, timeoutSec }`, copied verbatim from the §8.2 `202` reply; **`ctl.req.id === runId`** (binding, so both reporters pair on `opId = opIdFor(sessionId, runId)`) | `{ accepted: true }`; output and exit arrive as `pb.output` / `pb.end` on `ia.playbook` |
| `playbook.cancel` | `{ runId }` with `ctl.req.id = runId + ':cancel'` | `{ cancelled: boolean }` |

Agent checks before running (each failure => `ctl.res { ok: false, error }` and `playbook.run { ..., exit: null, error }`): `playbookId` in the §8.3 manifest (`not_allowed`); `sha256(utf8(body)) === bodyHash === manifest.bodyHash` (`hash_mismatch`); `requiresElevation === manifest.requiresElevation` and, when true, `self.elevation === 'admin'` (`elevation_required`); `ctl.req.id === runId` (`bad_args`); `args` re-validated with the same `validatePlaybookArgs` port (`bad_args`); at most one running playbook per session (`busy`).

**Argument rules (`validatePlaybookArgs`, shared, ported to Rust and Kotlin, fixtures `fixtures/agent/playbook-args.json`), enforced by the server and again by the agent:** `bool` -> `true` / `false`; `int` -> decimal, no sign for zero, `-` for negatives, no exponent, within `min`/`max`; `string` / `enum` as given after NFC, `<= 4000` chars, no C0 controls; **no** coercion from string to int/bool (`bad_args`); a `string` must match its anchored `pattern`; for `interpreter: 'cmd'` every string value must **additionally** match `^[A-Za-z0-9 ._:\\/-]{0,256}$` whatever the pattern says (the batch parser expands `%IA_PARAM_X%` textually, so `&`, `|`, `>`, `^`, `%` and newlines would inject commands); for `powershell` values are `<= 4096` chars with no `\u0000`. The values reach the script as `IA_PARAM_<NAME>=<canonical string>` environment variables: they are passed out of band and bodies must treat them as data; this makes injection a property of the body, not of the transport, which is why the editor lints bodies (§8.1) and `cmd` values are restricted.

**Execution (binding; the elevated instance never executes a file an unprivileged principal can write):**

| Interpreter / instance | Launch |
|---|---|
| `powershell`, any instance | the verified body is written to the child's **stdin** and the pipe closed: `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -Command -` (full System32 path, §14); no script file exists on disk at any time |
| `cmd`, user instance | `%LOCALAPPDATA%\IndiansAssist\run\<runId>.cmd`, `CREATE_NEW`, owner-only DACL (same principal as the runner, so nothing is gained by an attacker who is already that user), `cmd.exe /Q /c <path>`; deleted on exit |
| `cmd`, admin instance | the body is written into `%ProgramData%\IndiansAssist\run\` (created by the elevated instance with a DACL granting write to `Administrators` and `SYSTEM` only and a mandatory label `S:(ML;OICI;NW;;;HI)`, so medium-integrity same-user code cannot write up), file created `CREATE_NEW | FILE_SHARE_READ`, the handle **kept open** while the child is created `CREATE_SUSPENDED`; the agent re-reads and re-hashes the file through its own handle and compares with `bodyHash` **before** `ResumeThread`; deleted on exit. Windows test: a second process opening the run file for write while a run is in flight must fail |
| `requiresElevation: false` in the admin instance | the child is created with the **limited linked token** (`GetTokenInformation(TokenLinkedToken)` -> `CreateProcessAsUserW`, medium integrity, same user) so a non-elevated playbook never runs as administrator by accident; `ranAs: 'user'` |
| `requiresElevation: true` | admin instance only (`elevation_required` otherwise); `ranAs: 'admin'` |

Common: `CREATE_NO_WINDOW`, a dedicated job object (`CREATE_SUSPENDED` + `AssignProcessToJobObject` + resume, `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) so a timeout/cancel kills the whole tree; working dir `%LOCALAPPDATA%\IndiansAssist\run\` (user) or the `%ProgramData%` run dir (admin); environment = the agent's plus the `IA_PARAM_*` variables; stdout/stderr through pipes. `pb.end` and the chain carry `ranAs`.

| # | Rule |
|---|---|
| D1 | On a clean exit (**Stop**/**Quit**, session end, or the connect window closed before connecting) **and** when the Desk did not choose "Keep installed" (D5), the agent removes: its exe, its `.iaconfig` sidecar, the working directory `%LOCALAPPDATA%\IndiansAssist\` (logs, run temp, caches), and the HKCU protocol handler key (§2.5). | D3 | **Elevated hand-over child (§7):** it is the one that self-deletes when elevation was used (the user instance that handed over does **not** delete; exactly one instance deletes, decided by which holds the session at exit). | D4 | A crash (no clean exit) leaves the exe; the next start detects a stale `%LOCALAPPDATA%\IndiansAssist\session.lock` and offers "Finish removing IndiansAssist?". The lock carries a pid and a nonce **only**; the paths to delete are always the agent's fixed, derived locations and are never read from disk |
| D5 | "Keep IndiansAssist on this computer" opt-in (default off) in the pill menu and the ended view: copies the exe to `%LOCALAPPDATA%\IndiansAssist\IndiansAssist.exe`, keeps the HKCU handler, skips D1. | D6 | Nothing else is left behind: no registry outside `HKCU\Software\Classes\indiansassist` and the volatile `HKCU\Software\IndiansAssist\Volatile` key (§11.5; volatile keys vanish at logoff anyway and are deleted on exit), no Run key, no service, no firewall rule (outbound only), no Start Menu entry, no `%ProgramData%\IndiansAssist\` after an elevated exit |

### 11.4 Threading

One `tokio` multi-thread runtime for the WS client, the webrtc-rs peer and timers; capture and encode on dedicated OS threads (§4.1) feeding the peer through `tokio::sync::mpsc`; the egui UI on the main thread (eframe owns it) talking to the runtime over a channel pair. No blocking call runs on a runtime worker (capture, `SendInput`, file I/O and `powershell` spawning are on `spawn_blocking` or dedicated threads).

### 11.5 Single instance and config/log locations

A named mutex `Local\IndiansAssist.<userSid>` (`Local\`, never `Global\`: a `Global\` mutex is visible across terminal-server sessions) makes a second launch forward its `--code`/`--url` to the running instance over the pipe `\\.\pipe\IndiansAssist.<userSid>.<logonRand>` (§2.1 rank 1; `<userSid>` = the string SID of the process token user from `ConvertSidToStringSidW`, `<logonRand>` = 16 random hex bytes minted at first start of a logon and stored under the **volatile** key `HKCU\Software\IndiansAssist\Volatile\pipe`, so another user cannot predict the name) and exit; the hand-over child uses a distinct mutex suffix so it coexists briefly with the exiting parent. **Named-pipe squatting (binding):** `\\.\pipe\` is one machine-wide namespace, so a process of **another** user on a shared host could pre-create our pipe and receive the forwarded code. Server side: the agent creates the pipe with `FILE_FLAG_FIRST_PIPE_INSTANCE | PIPE_REJECT_REMOTE_CLIENTS` and a DACL granting only the current user SID; `ERROR_ACCESS_DENIED` / `ERROR_PIPE_BUSY` at creation means an instance the agent does not own exists, and the agent then runs without a pipe (second launches show their code in their own window instead of forwarding). Client side (the second launch): open with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` (the server can never impersonate the client), then before writing call `GetNamedPipeServerProcessId`, open that process and require (a) its token owner SID equal to the caller's and (b) `QueryFullProcessImageNameW` equal to the caller's own image path; otherwise drop the forward and show the code in the connect window. The pipe carries the `--code` / `--url` string only, validated with `normaliseTokenInput` by the receiver. Locations (all under `%LOCALAPPDATA%\IndiansAssist\`, all removed by self delete): `agent.log` (rotating 5 x 1 MiB; the A §6 redaction applies — SDP, ICE, tokens, hand-over values, clipboard and playbook output and keys never logged), `session.lock` (pid + nonce only), `run\` (cmd playbook temp of the user instance). Well-known keys are cached **in memory only** (§2.1); nothing else is cached on disk. No config persists between runs except, when D5 was chosen, the copied exe.

## 12. Android host (`apps/android`)

### 12.1 Shape

A single-activity Kotlin app, min SDK 29 (Android 10; `MediaProjection` token survival, scoped storage), target SDK latest, application id `com.indiansassist.desk`. It is a Desk of A §7 and a P3 agent of this document with the capability subset of §12.4, joining on a `p3_portable` token (§2, PRD 4). Libraries: `io.getstream:stream-webrtc-android` (Apache-2.0 wrapper over Google's libwebrtc, BSD-3-Clause), `kotlinx.serialization` (Apache-2.0) for wire types, OkHttp (Apache-2.0) WebSocket for `/signal`, Google Tink (Apache-2.0, **1.13+**, pinned) for the §1.3 handshake through its `subtle` classes, which are the only ones that accept a caller-supplied nonce and expose raw X25519 / HKDF: `com.google.crypto.tink.subtle.InsecureNonceXChaCha20Poly1305(key).encrypt(nonce, plaintext, aad)` / `.decrypt(nonce, ciphertext, aad)` (the public `Aead` API prepends a random nonce and cannot produce §1.3 frames), `com.google.crypto.tink.subtle.X25519.{generatePrivateKey, publicFromPrivate, computeSharedSecret}`, `com.google.crypto.tink.subtle.Hkdf.computeHkdf("HMACSHA256", ikm, salt, info, 32)`; `subtle` is documented by Tink as internal API, so the shared `sec-vectors.json` conformance test is the gate that catches a breaking Tink release (if `subtle` ever becomes unusable the fallback is `com.goterl:lazysodium-android`, ISC, to be added to the licence register at that time), AndroidX (Apache-2.0), `com.journeyapps:zxing-android-embedded` (Apache-2.0) for the QR scanner.

## 14. Security

| Asset / surface | Threat | Mitigation |
|---|---|---|
| The signed stub | a tampered exe is served, or the config trailer is forged | the exe is byte-identical per download and Authenticode-signed in CI; `manifest.sha256` is shown on the join page and verifiable by hand; the agent self-checks its own signature (`WinVerifyTrust`) and shows the signer (fatal in the elevated child, §2.6); the **trailer is not used** (§2.3, W1) so no post-signature bytes exist to forge; the sidecar is config, never code, parsed by a strict schema and **signed** by the region's key (§2.4) |
| Config/token tamper | a hostile `.iaconfig` or filename points the agent at an attacker's server or token; a planted generic sidecar hijacks later downloads; a deep link smuggles switches | a release build refuses an `apiOrigin` outside the compiled `IA_REGION_ORIGINS` unless the sidecar's Ed25519 `sig` verifies against the compiled region keys (the earlier `pubkeys` pin was circular and is gone); the generic `IndiansAssist.iaconfig` applies only to an exe named exactly `IndiansAssist.exe`; the filename code wins over a sidecar `code`; the sidecar is shredded after parse; a compact token is verified against the region's published Ed25519 key before any network call; the filename region must be a known region; `--url` takes the whole command-line tail and `--api-origin` does not exist in release builds (§2.5 L2); the knock still needs a human accept and then the Desk's consent, so a mis-pointed token cannot silently share |
| Join credential at rest | the download filename sits in Explorer, Search, Recent Items, browser history and cloud Downloads backup for the token's life | the filename carries a per-download **desk code**, never the dashboard short code or the compact token; it is valid only for native `desk.hello` / `public-lookup` and dies when the first session on the token reaches `active` (§2.2, §2.3). Residual: until then a reader of the filename can join as the Desk; the technician's accept and `token_busy` from the real Desk remain |
| Protocol-handler hijack | another app registers `indiansassist://`, or feeds a crafted URL | the handler is **HKCU** (per user, no admin), so a hijack needs code already running as the user (no privilege gained); `%1` is parsed from the entire command-line tail as one URL and only a token is extracted through `normaliseTokenInput`, never executed, never a second switch; a forwarded code during a live session is discarded; L3 tries the deep link automatically only after Keep; the same human accept + consent gate applies |
| Clipboard token leakage | the token sits on the clipboard (PRD 6 fast path), readable by any app and synced by Clipboard History / Cloud Clipboard; a synced clipboard carries a token or a password to the Assist | the join page writes **nothing** to the clipboard on its own and **Copy support code** copies the desk code only; the agent reads the clipboard once, only when ranks 1-3 are empty, clears the entry it consumed and otherwise never writes it; clipboard **sync** is default **off**, shows a toast per Desk->Assist sync, and redacts `ia1.<...>` compact tokens and Luhn-valid 12-digit groups to `[token removed]` both ways (§5.6); the token is short-lived and one-time where possible |
| Self-approval by injected input | the technician's `os.pointer` / `os.key` click the agent's own prompts (file accept, clipboard switch, monitor add, elevation Allow, Keep) or drag the pill away | low-level hooks drop the agent's own tagged (`IA_1`) events over agent windows and every prompt control is gated on physical input (§3.5); Android prompts use `filterTouchesWhenObscured` and a dispatch-window guard (§12.3); refused attempts are counted in `control.input.refused` |
| Elevation abuse | a technician elevates without cause, or injects into admin windows unseen; a modified agent floods hand-over mints; local code swaps the exe before UAC or seizes the session with the old resume key | elevation needs a typed reason (chained, both reporters), the Desk's **physical** Allow **and** Windows UAC; the hand-over token is API-minted, chained at mint, single-use through an atomic `consume`, bound to the session row, 120 s, one outstanding per session, 3 per 10 min, passed through an authenticated named pipe whose client pid is the launched child (§7.2); the hello must come from a native Windows client of the same arch that advertised `elevation`; the parent holds the exe handle through UAC, measures its hash and signer, and the child refuses on mismatch (fatal signer check); the server rotates the resume key on hand-over and closes the old socket `4411`; `elevation.requested/handover_minted/granted/denied/failed` are chained; the pill shows a shield; UAC prompts stay invisible (P8) so the agent can never click through a UAC dialog for the user; the residual is written in §7.4 |
| Playbook abuse / arbitrary code | an unapproved script runs; args inject a command; a same-user process edits the script between hash and launch of an elevated run | the agent runs only a body whose sha256 matches the manifest the **server** sent at `session.created` and the server refuses a body edited mid-session (`playbook_changed`); PowerShell bodies go to the interpreter over **stdin** (no file), elevated `cmd` bodies live in an admin-only, HI-labelled `%ProgramData%` directory with the handle held and re-hashed before `ResumeThread` (§8.4); non-elevated playbooks in the admin instance run under the limited token; `requires_elevation` is enforced against the real integrity level; args are canonicalised, pattern-checked and (for `cmd`) restricted to a safe character set, passed as `IA_PARAM_*` environment variables, never interpolated into the script text; bodies are linted; one run per session; output capped and never logged; every run is chained with its hash, exit and `ranAs`. P6 states honestly that `control` already permits arbitrary input and that the recording plus `input.text_burst` are the compensating record |
| Path traversal on file save | a crafted `file.offer` name escapes the folder | `sanitiseFileName` (A F5, shared vectors) plus the "leaf only" join rule and `bad_name` on any residual separator (§6.1 F3); files are `CREATE_NEW` into the dedicated folder only |
| DLL hijacking from the download folder | Windows resolves every **import-table** dependency before `main` runs, searching the exe's directory (Downloads) first for anything not on the KnownDLLs list; a planted `version.dll` or `dwmapi.dll` beside the stub runs as the user on double-click and, because §7.3 re-executes the same exe with `runas`, again inside the **elevated** child | load-time imports are restricted to the KnownDLLs set and CI fails the release build otherwise (import-table gate, §11.3); every other system library (`dxgi`, `d3d11`, `d3dcompiler_47`, `mfplat`, `mf`, `mfreadwrite`, `dwmapi`, `uxtheme`, `version`, `winmm`, `wintrust`, `dcomp`, `shcore`, `propsys`, ...) is loaded at run time **only** through `ia_platform::sys_lib(name)` = `LoadLibraryExW(name, NULL, LOAD_LIBRARY_SEARCH_SYSTEM32)` with `GetProcAddress`-resolved function tables, after `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)` and `SetDllDirectory("")` in `main`; the static CRT ships no DLL beside the exe; the embedded manifest declares no side-by-side dependency; the elevated child additionally refuses to start if `GetModuleFileNameW` of any loaded module is outside `%SystemRoot%` or its own image (§7.3 step 4). The gnu dev toolchain has no `/DELAYLOAD`, so late binding is the one mechanism on both toolchains (`docs/release.md`) |
| Secure-channel MITM | the signaling server rewrites DTLS fingerprints and the data-channel handshake | §1.3 binds key confirmation to both DTLS fingerprints, the session id and the key generation; the **commit round** gives a man in the middle one SAS guess per leg (1e-6 per handshake) instead of a grindable match; the console **gates control** behind the code confirmation per key generation and re-confirms after every rebuild (an attacker cannot wait for an unwatched rebuild); a passive or replaying server sees nothing (every channel but `ia.sec` is XChaCha20-Poly1305 under per-session keys it never holds; stated honestly, W7) |
| Privacy watermark | forensic tracing of misuse | the A §9 technician watermark is burned into the Assist view and the recording for P3 exactly as P1/A.2 (PRD 12.3); it stays |
| Data residency | session data leaving the region | unchanged (A T1-R6): the agent connects to the region's origin, the recorder stores in-region, audit stays in-region; the download grant and hand-over token live in the region's presence store only |
| Agent as local attack surface | a local port or pipe another app abuses; another user squats the pipe name on a shared host; a same-user process writes a file the elevated instance executes | the agent opens **no** listening socket; the single-instance pipe `\\.\pipe\IndiansAssist.<userSid>.<logonRand>` has an unpredictable per-logon suffix, is created `FILE_FLAG_FIRST_PIPE_INSTANCE \| PIPE_REJECT_REMOTE_CLIENTS` with a DACL granting only the current user, and its client verifies the server process's owner SID and image path before writing (§11.5); it carries only a `--code`/`--url` string, validated with `normaliseTokenInput`; the hand-over pipe authenticates its one client by pid (§7.2); the elevated instance never executes anything from a user-writable location: PowerShell over stdin, `cmd` from an admin-only HI-labelled directory, self delete by `MOVEFILE_DELAY_UNTIL_REBOOT`, no stub (§8.4, §10 D3) |

The pino `REDACT_PATHS` (api) gains `'*.handover'`, `'*.chunk'`, `'*.body'`, `'*.sas'`, `'*.deskCode'`, `'*.resumeKey'`; the agent's `tracing` redaction mirrors A §6 (SDP, ICE, tokens, hand-over, clipboard, playbook output, keys never logged).
